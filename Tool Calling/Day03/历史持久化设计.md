# Web 历史记录与轨迹持久化设计

> 设计日期：2026-11-05
> 状态：设计已确认，代码已实现（2026-11-05）
> 范围：Day03 Web 端；CLI 现有历史机制保持独立

## 1. 目标

让网页产生的每一轮问题、回答和完整 Tool Calling 轨迹保存到项目本地文件，并满足：

1. 刷新浏览器后，左侧历史和右侧轨迹自动恢复；
2. 服务重启后，历史仍然存在；
3. 可以查看任意历史轮次的完整轨迹；
4. 清空对话后，本地历史一并清除；
5. 不同浏览器/访问者之间不串历史；
6. 历史文件不进入 Git，不包含 API Key、system 提示词和内部异常堆栈。

## 2. 与现有需求的差异

原需求文档中有两处和本设计不同，需要产品确认后更新需求：

- **1.6.3**：原规定右侧只展示当前一轮轨迹；
- **1.10**：原规定“不提供轨迹历史列表”。

本设计将右侧轨迹区扩展为：

- 默认展示**最新一轮**轨迹；
- 点击左侧任意助手消息的“查看轨迹”，可切换查看历史轮次；
- 提供“回到最新”操作。

除这两点外，原需求中的 Token、耗时、失败、清空、响应式等规则继续适用。

## 3. 现状与差距

| 现状 | 问题 |
| --- | --- |
| `ConversationSession.messages` 只在内存中 | 服务重启后会话丢失 |
| 前端刷新时只渲染欢迎语 | 不会向后端读取已有消息 |
| `data/history.json` 只服务 CLI | Web 刷新无法使用 |
| `data/tracks.json` 只记录 CLI/成功轮次的原始消息 | 没有 turn_id、问题摘要、失败轮次和完整统计 |
| 右侧只渲染接口返回的当轮 trace | 没有历史轨迹查看入口 |
| 当前全局单会话 | 公开访问时不同浏览器会混用上下文 |

## 4. 总体架构

```text
浏览器（同一个域名）
  │  Cookie: weather_session_id=<uuid>
  ▼
FastAPI app.py
  ├─ SessionManager
  │    ├─ 按 session_id 加载/缓存 SessionState
  │    ├─ 每个会话独立的 asyncio.Lock / processing
  │    └─ 调用 WebHistoryStore 读写 JSON
  ├─ POST /api/chat       → 执行一轮 + 保存 turn
  ├─ GET  /api/history    → 返回当前会话的轮次摘要
  ├─ GET  /api/history/{turn_id} → 返回该轮完整 trace
  └─ POST /api/clear      → 清空当前会话历史
  ▼
data/web_sessions/<session_id>.json
```

- 浏览器只需持有 Cookie，不接触文件路径；
- 服务端根据 Cookie 决定读写哪个会话文件；
- 单进程内每个会话一把锁；固定 `--workers 1`；
- Caddy 提供 HTTPS 和访问密码（配置模板见 `deploy/Caddyfile.example`）。

## 5. 数据模型

### 5.1 会话文件

路径（可用 `WEB_HISTORY_DIR` 环境变量覆盖根目录）：

```text
data/web_sessions/<session_id>.json
```

结构：

```json
{
  "version": 1,
  "session_id": "8f14e45fceea167a5a36dedd4bea2543",
  "created_at": "2026-11-05T12:00:00.000Z",
  "updated_at": "2026-11-05T12:03:10.500Z",
  "turns": [
    {
      "turn_id": "a1b2c3d4e5f6",
      "turn_index": 1,
      "question": "北京天气怎么样？",
      "answer": "北京当前……",
      "status": "success",
      "created_at": "2026-11-05T12:01:00.000Z",
      "finished_at": "2026-11-05T12:01:03.200Z",
      "trace": {
        "trace_id": "trace123",
        "question": "北京天气怎么样？",
        "status": "success",
        "stop_reason": "completed",
        "tokens": { "...": "..." },
        "rounds": [ "...完整工具轮次..." ]
      }
    }
  ]
}
```

### 5.2 字段规则

| 字段 | 规则 |
| --- | --- |
| `session_id` | 服务端生成的 UUID4 hex，只允许 `[0-9a-f]{32}`；不接收客户端任意路径 |
| `version` | 数据格式版本，当前为 `1`，便于以后迁移 |
| `turns` | 按时间顺序保存；`turn_index` 从 1 开始 |
| `question` / `answer` | 用于恢复左侧消息和模型上下文 |
| `status` | `success` / `partial` / `failed` |
| `trace` | 服务端 `TraceRecorder` 返回的完整轨迹；不在列表接口中返回 |
| `answer` 为 `null` | 表示该轮失败；前端从 `trace.error.message` 生成失败气泡 |
| 文件权限 | 目录 `0700`、文件 `0600`；`data/` 已被 `.gitignore` 忽略 |

### 5.3 消息与模型上下文

不单独保存 `messages`，由 `turns` 派生，避免两份数据不一致：

- 左侧消息：所有 turns 依次渲染 user + assistant（失败轮次显示失败信息）；
- 模型上下文：只取有 `answer` 且 `status != failed` 的轮次，构造
  `[system] + [user, assistant, user, assistant, ...]`；
- 失败轮次继续在左侧展示，但不进入后续模型上下文（保持现有行为）。

## 6. 存储层设计

新增 `web_history.py`：

```python
class WebHistoryStore:
    def load(session_id: str) -> SessionState
    def save(state: SessionState) -> None
    def append_turn(session_id: str, turn: StoredTurn) -> None
    def clear(session_id: str) -> None
```

要求：

1. **原子写**：先写同目录临时文件，再 `os.replace`；
2. **文件锁**：`SessionManager` 为每个会话提供 `asyncio.Lock`；同一会话的
   chat / clear / history 写操作串行；
3. **容错**：JSON 损坏时把文件重命名为 `.corrupt-<timestamp>`，记录日志并返回空会话；
4. **路径安全**：`session_id` 必须匹配 UUID hex，不接受 `../` 等路径；
5. **不提交 Git**：`data/` 已在 `.gitignore`；
6. **权限**：创建目录 `0700`，文件 `0600`；
7. **容量控制**：默认保留全部轮次；后续可增加
   `MAX_TURNS_PER_SESSION` 和过期会话清理（建议 180 天）。

## 7. 会话标识

使用 HttpOnly Cookie：

```text
weather_session_id=<32位hex>
```

- `HttpOnly`：前端 JS 不可读取；
- `SameSite=Lax`：降低跨站请求风险；
- `Secure`：生产 HTTPS 开启；
- `Path=/`；
- `Max-Age=180 天`；
- Cookie 不存在时自动创建新会话并写回；
- `session_id` 只从 Cookie 读取，**不接受**查询参数或请求体指定；
- `POST /api/clear` 清空后可以轮换新 session_id，避免旧 ID 再次加载旧数据。

> 部署时浏览器通过 Caddy HTTPS 访问；FastAPI 根据 `X-Forwarded-Proto`
> 或配置项决定是否设置 `Secure`。

## 8. API 设计

### 8.1 `POST /api/chat`

请求：

```json
{ "question": "北京天气怎么样？" }
```

成功/业务失败响应在现有字段基础上增加：

```json
{
  "ok": true,
  "answer": "北京当前……",
  "trace": { "...": "..." },
  "turn_id": "a1b2c3d4e5f6",
  "history_saved": true
}
```

规则：

1. 400 空输入：不创建 turn，不写文件；
2. 409 忙碌：不创建 turn，不写文件；
3. 200 成功 / 部分成功 / 业务失败：创建 turn，写入会话文件后返回；
4. 写文件失败：仍返回回答与 trace，但 `history_saved=false`，前端显示
   “本轮回答已生成，但历史保存失败”；
5. 未预期 500：不创建 turn；
6. `turn_id` 由服务端生成，前端不可指定。

### 8.2 `GET /api/history`

返回当前 Cookie 会话的轮次摘要，**不返回完整 trace**：

```json
{
  "ok": true,
  "session_id": "8f14e45fceea167a5a36dedd4bea2543",
  "turns": [
    {
      "turn_id": "a1b2c3d4e5f6",
      "turn_index": 1,
      "question": "北京天气怎么样？",
      "answer": "北京当前……",
      "status": "success",
      "created_at": "2026-11-05T12:01:00.000Z",
      "finished_at": "2026-11-05T12:01:03.200Z",
      "has_trace": true,
      "error_message": null
    }
  ]
}
```

- 按 `turn_index` 升序返回，便于恢复消息顺序；
- 没有历史时返回空数组；
- 失败轮次返回 `error_message`，前端无需额外请求即可恢复失败气泡。

### 8.3 `GET /api/history/{turn_id}`

返回该轮完整记录：

```json
{
  "ok": true,
  "turn": {
    "turn_id": "a1b2c3d4e5f6",
    "question": "北京天气怎么样？",
    "answer": "北京当前……",
    "status": "success",
    "created_at": "2026-11-05T12:01:00.000Z",
    "finished_at": "2026-11-05T12:01:03.200Z",
    "trace": { "...完整轨迹..." }
  }
}
```

- 只允许查当前 Cookie 会话内的 turn；
- 不存在或不属于当前会话返回 404；
- 不返回其他浏览器的历史。

### 8.4 `POST /api/clear`

- 清空当前会话的 turns 和消息；
- 删除或原子重写当前会话文件；
- 返回 `{ "ok": true }`；
- 可选：轮换新的 `weather_session_id` Cookie；
- 不影响 CLI 的 `data/history.json` / `data/tracks.json`，也不删除 `data/meeting_rooms.json`。

## 9. 前端设计

### 9.1 首次加载 / 刷新

```text
页面加载
  → GET /api/history
  → 有历史：
       恢复全部用户/助手消息
       默认加载最新一轮 trace
       每轮助手消息附带“查看轨迹”按钮
  → 无历史：
       显示欢迎语和“等待用户提问”
```

- 加载中显示“正在读取历史记录…”；
- 请求失败显示可读提示，不覆盖已有页面；
- 恢复消息后自动滚动到最新一条；
- 失败轮次显示失败气泡，不生成“查看轨迹”以外的额外内容。

### 9.2 查看历史轨迹

- 每轮助手消息下方增加“查看轨迹”按钮；
- 点击后：

```text
GET /api/history/{turn_id}
  → 右侧轨迹区渲染该轮完整 trace
  → 顶部显示“正在查看第 N 轮历史轨迹”
  → 提供“回到最新”按钮
```

- 右侧默认仍展示最新一轮；
- 查看历史时，左侧输入区保持可用；
- 用户发送新问题时，右侧退出历史查看状态，先显示本轮执行中，完成后显示最新轨迹；
- 历史轨迹与最新轨迹使用同一套渲染函数（概览 + 轮次 + 工具详情）。

### 9.3 清空

- 确认文案更新为：“确定清空当前对话、历史记录和本轮轨迹吗？”
- 确认后调用 `/api/clear`；
- 成功：清除本地消息、历史按钮、右侧轨迹，显示欢迎语；
- 取消或失败：保持现状。

### 9.4 历史数量较多时

- 消息区继续使用现有独立滚动；
- 仅为每轮提供一个轻量按钮，不在页面顶部另建大列表；
- 需要快速跳转时，可后续增加“历史提问”折叠列表；
- 轨迹详情按需请求，避免首次加载全部 trace。

## 10. 保存时机与失败处理

在 `POST /api/chat` 内：

1. 完成模型与工具执行，得到 `RunResult`；
2. 生成 `turn_id` 与 `StoredTurn`；
3. 追加到内存会话；
4. 原子写入会话文件；
5. 返回回答 + trace + `turn_id` + `history_saved`。

保存失败时：

- 服务端记录日志；
- 回答仍然返回；
- `history_saved=false`；
- 前端显示一次性警告；
- 不把失败的 turn 说成已保存。

## 11. 安全与隐私

- 历史文件位于 `data/web_sessions/`，`data/` 已被 `.gitignore` 忽略；
- 文件权限 600，目录 700；
- Cookie 为 HttpOnly，不允许前端读取 session_id；
- API 只根据 Cookie 定位会话，不接受客户端拼路径；
- 历史内容只包含问题、回答、工具参数/结果和统计，不包含 system 提示词、API Key、异常堆栈；
- 前端继续使用 `textContent`/DOM API 渲染历史，禁止 `innerHTML` 拼接；
- 公开部署建议继续使用 `deploy/Caddyfile.example` 中的 Caddy Basic Auth + HTTPS；
- 当前没有账号体系：知道访问密码的人可以创建各自会话，但没有用户级权限；
- 若要多用户公开使用，需要进一步增加登录、会话归属、限流和审计。

## 12. 迁移与兼容

- CLI 的 `data/history.json`、`data/tracks.json` 保持原样，不迁移到 Web 历史；
- Web 历史是全新目录，首次访问自动创建；
- 现有 Web 内存会话没有持久化数据，升级后刷新会得到新会话；
- `UserService` 目前会向 `data/tracks.json` 追加 CLI 轨迹；Web 端应传入
  “不写 Tracks”选项，避免与 `data/web_sessions` 重复保存；CLI 行为不变；
- 数据格式带 `version`，后续可做迁移脚本。

## 13. 并发与性能

- 固定单 worker；每个会话独立锁，避免不同用户互相阻塞；
- 同一会话的 chat / clear / history 写操作串行；
- 列表接口不返回完整 trace，减少首屏流量；
- trace 按需加载；
- 单会话轮次很多时，可增加分页或只恢复最近 N 轮（默认保留全部，后续配置化）；
- 若改为多 worker，必须使用文件锁（`filelock`）或 Redis/数据库。

## 17. 风险与决策

| 风险/决策 | 处理 |
| --- | --- |
| 原需求要求右侧只展示当前一轮 | 本设计作为扩展需求，需产品确认并更新 1.6.3、1.10 |
| 公开 `0.0.0.0` 无登录 | 继续用 Caddy Basic Auth；多用户需后续登录体系 |
| 内存会话与文件双写不一致 | 文件为事实来源；启动时从文件重建；写失败明确提示 |
| 多 worker 拆分会话 | 固定单 worker；改用多 worker 时加文件锁或 Redis |
| 历史文件过大 | trace 按需加载；后续增加轮次上限/TTL/清理任务 |
| 用户清空后仍想恢复 | 清空即删除当前会话数据，不做软删除；如需回收站另设计 |
| 浏览器禁用 Cookie | 无法跨刷新识别会话，页面提示历史不可用 |
