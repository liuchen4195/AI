## 1. 目标与范围

### 1.1 目标

在不破坏现有命令行助手的前提下，为 Day03 增加一个浏览器页面：

1. 左侧连续对话，保留当前会话全部消息；
2. 右侧只展示最近一次提问产生的真实 Tool Calling 轨迹；
3. 轨迹包含轮次、串行/并行、参数、结果、开始/结束时间、耗时、Token、状态与停止原因；
4. 所有时间与 Token 必须来自真实运行记录，缺失时明确显示“未记录”或“未返回”；
5. 支持失败、部分成功、清空对话、移动端单列与键盘操作。

### 1.2 不在本次范围

- 登录、多用户、云端同步；
- 文件/图片/语音上传；
- 轨迹历史列表；
- 跨轮累计 Token；
- 修改工具参数后重跑；
- 流式输出（SSE/WebSocket）。本轮采用请求/响应模式，处理中状态由前端展示。

### 1.3 核心设计原则

- **后端是唯一事实来源**：对话历史、工具白名单、轨迹统计都由后端掌握，前端只负责展示。
- **先记录，再展示**：页面不得推断耗时、并发或 Token；没有记录就显示“未记录/未返回”。
- **一轮一轨迹**：每次有效提问生成一条独立 Trace，后端只返回本轮 Trace。
- **失败可解释**：错误信息对用户可理解，且不泄露 Key、系统提示词和本机路径。

## 3. 总体架构

### 3.1 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| Web 框架 | FastAPI + Uvicorn | 与现有异步工具链一致，接口定义清晰，静态文件托管简单 |
| 模型客户端 | `AsyncOpenAI` | 避免同步请求阻塞事件循环；若兼容性有问题可退回 `asyncio.to_thread` |
| 前端 | 原生 HTML/CSS/JavaScript | 无构建步骤，便于教学与演示，满足单页需求 |
| 轨迹采集 | 新增 `trace.py` | 与业务循环解耦，可单独测试 |
| 会话存储 | 进程内单会话 | 需求不含多用户/持久化；重启后清空可接受 |
| 测试 | pytest + FastAPI TestClient | 覆盖轨迹规则与接口行为 |

### 3.3 请求流程

```text
浏览器
  │ 1. 本地校验非空
  │ 2. 立即清空右侧旧轨迹，左侧追加用户消息 + 等待状态
  ▼
POST /api/chat {question}
  ▼
FastAPI app.py
  ├─ 获取会话锁（忙则 409）
  ├─ 服务端再次校验
  ├─ TraceRecorder.start(question)   ← 本轮开始时间
  ├─ UserService.run(session.messages, question, recorder)
  │    ├─ 模型请求（记录次数、耗时、usage）
  │    ├─ 有 tool_calls：开启工具轮次 → 并发执行 → 记录每个调用
  │    └─ 无 tool_calls：最终回答 → 记录结束
  └─ 返回 { ok, answer, trace }
  ▼
浏览器
  ├─ 成功：替换等待气泡为回答；渲染本轮轨迹；自动滚动
  ├─ 业务失败：显示失败气泡与失败轨迹；输入内容恢复
  └─ 网络/HTTP 失败：右侧保持“本轮失败”，绝不恢复上一轮轨迹
```

## 4. 数据契约设计

### 4.1 服务层返回结构

`UserService.run()` 不再返回 `str | None`，改为返回：

```python
@dataclass
class RunResult:
    ok: bool                 # 是否拿到最终回答
    answer: str | None       # 最终回答；失败为 None
    trace: dict              # 本轮轨迹（见 4.2）
```

- 模型请求异常、达到轮次/数量限额：返回 `ok=False` 和带失败信息的 `trace`，不再向 Web 层抛异常。
- 只有真正未预期的内部错误才由 API 层兜底为 500。

### 4.2 Trace JSON 结构

```json
  "error": null

```

### 4.3 字段与状态定义

| 字段 | 规则 |
| --- | --- |
| `status` | `success`（有最终回答且无工具失败）/ `partial`（有最终回答但至少一个工具失败）/ `failed`（无最终回答）。`running` 仅保留给未来流式方案，当前接口不返回 |
| `stop_reason` | `completed` / `model_request_failed` / `empty_answer` / `max_model_rounds` / `max_tool_rounds` / `tool_call_limit` / `city_limit` / `internal_error` |
| `model_requests` | 本轮实际发起的模型请求次数，失败的请求也计数 |
| `model_duration_ms` | 本轮所有模型请求耗时之和；用于诊断，页面可不展示 |
| `tool_calls` | 本轮实际执行或尝试执行的工具调用总数，包含失败与被拒绝的调用 |
| `tool_rounds` | 模型返回过 `tool_calls` 的轮次数量，不等于模型请求次数 |
| `execution_mode` | 根据真实执行记录推导：`none` / `serial` / `parallel` / `mixed`（规则见 6.4） |
| `duration_ms` | 从服务端接受有效问题到最终回答或确认失败；整数毫秒 |
| `tokens` | 只累加模型服务 `usage` 实际返回值；无任何返回时为 `null`；部分请求缺失时 `complete=false` |
| `rounds[].mode` | 该轮 `call_count > 1` 为 `parallel`，否则为 `single` |
| `calls[].status` | `success` / `error` / `rejected`；未执行或超限不得显示成功 |
| `calls[].error_type` | `tool_not_found` / `argument_parse_failed` / `validation_failed` / `timeout` / `tool_execution_failed` / `tool_reported_error` |
| `calls[].execution` | `parallel`（同轮多调用）/ `serial`（单调用轮次）；仅描述调用方式，不代表完成顺序 |
| `error` | 致命错误：`{type, message, stage, round}`；工具级错误写在各 `call` 上 |

### 4.4 时间与 Token 采集规则

- **墙钟时间**：`datetime.now(timezone.utc).isoformat(timespec="milliseconds")`，前端转本地时间显示。
- **耗时**：`time.perf_counter()` 差值，四舍五入为整数毫秒。
- **开始时间**：服务端接受有效问题之后的第一个动作。
- **结束时间**：拿到最终回答，或确认失败的那一刻。
- **并行轮次耗时**：记录该轮 `gather` 的整体墙钟时间，不用各调用耗时相加。
- **未记录**：字段为 `null`，前端显示“未记录”。
- **Token**：每次模型响应读取 `usage.prompt_tokens / completion_tokens / total_tokens`；
  - 全部请求都返回用量：展示累计值；
  - 部分请求返回：展示已返回部分的累计值，并标注“部分请求未返回”；
  - 全部未返回：显示“未返回”，绝不显示 `0`；
  - `total` 优先用服务商返回的 `total_tokens`，缺失时用 `input + output`（两者均为实际返回值，不是按字符估算）。
- **工具函数与天气接口本身不产生 Token**，不参与统计。

## 5. 接口设计

### 5.1 `GET /`

返回 `static/index.html`。

### 5.2 `GET /api/health`

```json
{ "ok": true }
```

### 5.3 `POST /api/chat`

请求体：

```json
{ "question": "北京天气怎么样？" }
```

成功或业务失败统一返回 200：

```json
{
  "ok": false,
  "answer": null,
  "trace": { "...": "本轮失败轨迹" }
}
```

状态码约定：

| 状态码 | 场景 | 前端处理 |
| --- | --- | --- |
| 200 | 本轮处理完成（无论成功/部分成功/业务失败） | 渲染回答或失败信息 + 本轮轨迹 |
| 400 | 问题为空或只有空白 | 视为输入错误：保留输入、恢复上一轮轨迹（若有快照） |
| 409 | 上一轮仍在处理 | 提示“正在处理中”，不覆盖当前轨迹 |
| 500 | 未预期内部错误 | 右侧显示“本轮失败，未获取到轨迹”，不恢复旧轨迹 |

非 200 错误统一返回结构化错误，不包含异常堆栈：

```json
{
  "ok": false,
  "error": {
    "type": "invalid_input | busy | internal_error",
    "message": "用户可读的错误说明"
  }
}
```

服务端规则：

1. 问题 `strip()` 后为空直接 400，不创建 Trace；
2. 使用 `processing` 标志 + `asyncio.Lock` 双重保护；处理中返回 409；
3. 客户端不能提交历史消息、system 提示或工具列表：`ChatRequest` 设置 `extra="forbid"`，只接受 `question`；
4. 成功后将 `user` + `assistant` 两条纯文本消息追加进会话上下文；
5. 失败轮次不写入模型上下文，但前端仍展示该轮用户消息和失败回答；
6. 返回的 `trace` 只属于当前这一轮。

### 5.4 `POST /api/clear`

```json
{ "ok": true }
```

- 处理中返回 409；
- 成功后会话恢复为只含 `system` 的初始状态；
- 不删除 `data/` 下任何文件，不影响天气数据源；
- 前端必须用户确认后才调用。

## 6. 前端设计

### 6.1 页面结构

```text
┌──────────────────────────────────────────────────────────────┐
│ 天气查询助手                                   [清空对话]      │
├───────────────────────────────┬──────────────────────────────┤
│ 对话区域                       │ 本轮调用轨迹                  │
│ 消息列表（独立滚动）            │ 概览卡片（问题/状态/统计）      │
│                               │ 轮次列表                      │
│                               │ 工具调用卡片（独立滚动）        │
├───────────────────────────────┤                              │
│ [输入框                    ][发送] │                          │
└───────────────────────────────┴──────────────────────────────┘
```

- DOM 顺序：先对话、后轨迹，保证手机端自然顺序；
- 桌面端 CSS Grid 双栏，两栏各自滚动；
- 手机端（`max-width: 900px`）单列，页面自然滚动，禁止页面级横向滚动；
- 输入框在对话面板底部，移动端使用 `position: sticky` 保持在可视区域底部。

### 6.2 页面状态机

| 状态 | 对话区 | 轨迹区 | 输入 |
| --- | --- | --- | --- |
| 初始 | 欢迎语 | “等待用户提问” | 可用 |
| 输入错误 | 提示“请输入要查询的问题” | 保留上一轮轨迹 | 可用，内容保留 |
| 正在处理 | 用户消息 + 等待气泡 | 已清空，显示“本轮正在执行…” | 禁用 |
| 查询成功 | 最终回答 | 完整本轮轨迹 | 恢复可用 |
| 部分成功 | 基于成功结果的回答 | 成功/失败调用分别标记 | 恢复可用 |
| 查询失败 | 失败气泡 | 失败阶段、已记录耗时与统计 | 恢复可用 |
| 清空完成 | 欢迎语 | “等待用户提问” | 恢复可用，聚焦 |

### 6.3 对话区交互规则

- 输入框使用 `textarea`；`Enter` 发送，`Shift+Enter` 换行；
- 判断 `event.isComposing`，中文输入法组合期间按 Enter 不发送；
- 发送前 `trim()` 校验；为空/纯空格显示 `role="alert"` 提示，不发送、不清空轨迹；
- 有效提交后：缓存草稿 → 清空输入框 → 追加用户消息和助手等待气泡 → 清空右侧轨迹 → 显示执行中 → 禁用发送按钮；
- 响应成功：用真实回答替换等待气泡；
- 业务失败（200 + `ok:false`）：等待气泡替换为失败信息，输入框恢复问题内容并聚焦；
- 网络/HTTP 错误：等待气泡替换为可理解错误；右侧显示本轮失败占位，**不得恢复上一轮轨迹**；输入内容恢复；
- 服务端 400（输入错误）：恢复上一轮轨迹快照（仅此一种情况恢复），并提示输入错误；
- 每次新增消息后自动滚动到最新位置；用户正在向上翻阅时可暂停自动滚动（可选优化）；
- 新问题不会删除左侧已完成消息；
- 清空对话：`confirm("确定清空当前对话和本轮轨迹吗？")`；取消则什么都不变；确认且服务端成功后才重置前端。

### 6.4 轨迹区展示规则

**概览卡片**必须展示：

- 本轮用户问题；
- 状态：处理中 / 成功 / 部分成功 / 失败（文字 + 图标，不能只用颜色）；
- 模型请求次数、工具调用次数、工具调用轮数；
- 调用方式：未调用工具 / 串行调用 / 并行调用 / 混合调用；
- 本轮开始时间、结束时间、总耗时；
- 输入 Token、输出 Token、总 Token；
- 停止原因。

调用方式推导（只看真实记录，不看工具名称）：

| 条件 | 概览显示 |
| --- | --- |
| `tool_calls == 0` | 本轮未调用工具 |
| 只有 1 个工具轮次且该轮多调用 | 并行调用 |
| 所有工具轮次都是单调用 | 串行调用 |
| 同时存在多调用轮次和多个工具轮次 | 混合调用 |
| 只有 1 个工具轮次且单调用 | 串行调用（单工具） |

**轮次与工具卡片**：

- 按真实执行顺序展示“第 N 轮 · X 个工具 · 并行调用/单工具调用”；
- 同一轮中多个工具显示为并行，但**不得把列表顺序描述成完成顺序**；完成先后以各自结束时间为准；
- 每个工具卡片展示：名称、用途说明、调用编号、所属轮次、串行/并行、状态、参数、结果、错误类型与信息、开始时间、结束时间、耗时；
- 参数和结果使用原生 `<details>/<summary>` 默认折叠，展开后显示格式化 JSON；
- 错误信息不折叠，直接显示；
- 本轮未调用工具时显示“本轮未调用工具”，但概览中的模型请求次数、耗时、Token 仍然展示。

### 6.5 时间与 Token 的显示格式

- 开始/结束时间：本地时间 `YYYY-MM-DD HH:mm:ss.SSS`；
- 耗时：`< 1000 ms` 显示 `640 ms`；`>= 1000 ms` 显示 `1.24 s（1240 ms）`；
- 缺失：统一显示“未记录”；
- Token：千分位显示；缺失显示“未返回”；部分缺失追加“（部分请求未返回）”；
- 处理中的工具不得提前显示最终耗时。

### 6.6 长内容、滚动与布局

- 网格子项设置 `min-width: 0`，防止长 JSON 撑破页面；
- `<pre>` 使用 `white-space: pre-wrap; word-break: break-word; overflow: auto; max-height: 240px;`；
- 桌面端左右面板高度固定为视口剩余高度，各自 `overflow-y: auto`；
- 手机端页面只纵向滚动，不出现页面级横向滚动。

### 6.7 可访问性

- 状态徽标同时包含文字与符号，不依赖颜色；
- 对话区与轨迹区使用 `aria-live="polite"`；处理中设置 `aria-busy="true"`；
- 错误提示使用 `role="alert"`；
- 按钮使用原生 `<button>`，保留清晰焦点样式；
- `<details>/<summary>` 自带键盘展开能力；
- 清空确认使用浏览器原生 `confirm`，支持 Enter/Esc；
- 尊重 `prefers-reduced-motion`，关闭不必要的平滑滚动动画。

## 9. 关键设计决策与风险

| 决策/风险 | 处理方式 |
| --- | --- |
| 同步 OpenAI 客户端阻塞事件循环 | 改用 `AsyncOpenAI`；不兼容时用 `asyncio.to_thread` |
| 是否持久化 Web 会话 | 原方案不做；扩展设计见 `历史持久化设计.md`（会话文件 + Cookie） |
| 是否流式输出 | 不做；处理中状态由前端展示，长请求持续显示“处理中” |
| 失败轮次是否进入模型上下文 | 不进入；前端仍显示该轮消息，避免无回答的 user 消息污染上下文 |
| 一次请求中部分 Token 缺失 | 展示已返回部分并标注“部分请求未返回”，不伪造、不补 0 |
| 工具“业务失败”的判定 | 抛异常或返回 `status: "error"` 均视为该调用失败 |
| 部分成功定义 | 有最终回答且至少一个工具失败 = partial |
| 限额触发后的处理 | 超额调用标记 `rejected`，不执行，以对应 `stop_reason` 结束，避免页面误判成功 |
| 客户端网络失败 | 右侧展示本轮失败占位，绝不恢复上一轮轨迹 |
| 输入非法 | 前端本地拦截，不清轨迹；服务端 400 时前端恢复上一轮轨迹快照 |
| 大结果破坏布局 | `min-width: 0` + `<pre>` 换行 + 内部滚动；不截断真实结果 |
| 并发重复提交 | 前端 `isProcessing` 禁用 + 后端 `asyncio.Lock` 双重保护 |
| 多用户/公网暴露 | 原方案仅绑定 `127.0.0.1`；域名部署模板见 `deploy/`，多会话隔离见 `历史持久化设计.md` |

## 11. 扩展设计：Web 历史与轨迹持久化

> 完整方案见 [`历史持久化设计.md`](历史持久化设计.md)。
> 状态：设计已确认，代码已实现（2026-11-05）。

本扩展解决当前 Web 端的三个问题：

1. 会话只存在内存，服务重启后丢失；
2. 浏览器刷新不会向后端加载已有消息；
3. 右侧只能看当轮轨迹，不能回看历史轮次。

设计要点：

- 每个浏览器通过 HttpOnly Cookie `weather_session_id` 标识会话；
- 每轮问题和完整 trace 保存到 `data/web_sessions/<session_id>.json`；
- 新增 `GET /api/history`、`GET /api/history/{turn_id}`；
- 页面加载时恢复左侧消息，并默认展示最新一轮轨迹；
- 每轮助手消息提供“查看轨迹”，右侧显示历史轨迹和“回到最新”；
