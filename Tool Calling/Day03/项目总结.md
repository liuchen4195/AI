# Day03 天气/空气质量/会议室助手 — 项目总结

> 基于实际代码（`app.py`、`prompt.py`、`main.py`、`model.py`、`service.py`、`trace.py`、`tools.py`、`history.py`、`tracks.py`、`static/index.html`、`data/meeting_rooms.json`）整理，不含推测。

## 项目解决什么问题

一个**带工具调用（Tool Calling）闭环的 AI 助手**：用户用自然语言提问，模型通过调用真实工具获取数据后作答，覆盖三类信息：

- **城市天气**（open-meteo 免费 API）
- **城市空气质量**（open-meteo 免费 API）
- **会议室信息**（本地 JSON 数据 `data/meeting_rooms.json`，共 6 间会议室）

当前已具备命令行入口和 Web 服务入口（步骤 3：静态页与健康检查），网页对话与轨迹展示将在后续步骤实现。

核心工程问题：**让模型不凭记忆编造事实**——模型只负责决定"调用哪个工具、传什么参数"，数据一律来自工具的真实返回（`prompt.py` SYSTEM_PROMPT 明确要求"不得凭记忆生成坐标、天气、PM2.5、PM10、AQI 或会议室信息"）。同时处理了多轮工具调用的受控循环、并行调用、参数校验、历史持久化、轨迹统计与错误脱敏等问题。

## 整体流程

**CLI**：`main.py` 交互循环 → `service.py` 的 `UserService.run()` 受控循环（最多 10 轮模型调用，返回 `RunResult(ok, answer, trace)`）→ `trace.py` 的 `TraceRecorder` 同步记录模型请求耗时/Token 与工具轮次/调用 → 模型返回 `tool_calls` → `run_tools()` 白名单查 `tools_map`、JSON 解析、Pydantic 校验、执行工具 → 结果回传给模型 → 模型给最终回答 → 存入历史/轨迹。

**Web（步骤 3）**：`uvicorn app:app` → `app.py` 托管 `/static` 与首页 → `GET /api/health` 健康检查；`ConversationSession` 已持有 `[system]` 消息和 `asyncio.Lock`，等待步骤 4 接入 `/api/chat`。

## 逐文件说明

### `app.py` — Web 入口（步骤 3）

- **FastAPI 应用**：`app = FastAPI(title="天气查询助手")`，默认 `uvicorn.run(app, host="127.0.0.1", port=8000)`。
- **`ConversationSession`**：
  - `messages` 启动时为 `[{"role": "system", "content": SYSTEM_PROMPT}]`；
  - `lock` 为 `asyncio.Lock`，供步骤 4 的并发保护使用；
  - `add_turn(question, answer)` 只追加 user/assistant 两条最终消息，不保存 tool_calls/tool 消息；
  - `reset()` 恢复为只含 system 的初始状态。
- **`app.state.session`**：保存单会话实例。
- **路由**：
  - `GET /`：返回 `static/index.html`；
  - `GET /api/health`：返回 `{"ok": true}`，不暴露会话和提示词；
  - `/static`：由 `StaticFiles` 托管。
- **配置校验**：导入 `service` 时校验 `OPENAI_API_KEY / OPENAI_MODEL / BASE_URL`，缺失则启动失败并报明确错误。

### `prompt.py` — 共用系统提示词

- **`SYSTEM_PROMPT`**：从 `main.py` 抽出的行为规则，CLI（`main.py`）和 Web（`app.py`）共用。
  - 成功标准：先调 `get_city_pos` 拿真实坐标再查天气/空气质量；会议室先调 `get_room_info`；互不依赖的查询可同轮并行；最终回答只用工具结果并说明数据时间和单位。
  - 边界：不得编造数据；城市歧义时反问用户；最多处理 5 个城市，不访问用户提供的任意 URL；工具失败如实说明；不给医疗建议。

### `main.py` — CLI 交互入口

- **`SYSTEM_PROMPT`**：已移到 `prompt.py`，`main.py:5` 直接导入。
- **`main()`**（`main.py:8-91`）：`asyncio` 入口。创建 `UserService` 和 `History`（读 `data/history.json`），拼出 `[system, *历史]` 消息列表，死循环读用户输入。
  - 每次调用 `service.run(messages, user)` 前用 `time.perf_counter()` 计时；`run()` 现在返回 `RunResult`。
  - 成功后把 user/assistant 两条消息追加进内存并 `history.save(messages[1:])`（去掉 system 存盘）；`result.ok` 为 False 时不存历史。
- **斜杠命令**（均在 `main()` 内）：
  - `/history`：打印历史轮数及截断到 120 字符的逐条消息（`main.py:21-36`）。
  - `/clear`：保留 system，清空内存和文件历史（`main.py:38-44`）。
  - `/rooms`：调 `load_meeting_rooms()` 打印全部会议室（名称/楼层/容量/地址/设备，`main.py:46-58`）。
  - `/help`：打印帮助（`main.py:60-67`）。

### `static/index.html` — 最小页面骨架

- 步骤 3 只提供标题和占位文字；完整的双栏对话/轨迹布局由步骤 6 实现。

### `model.py` — 工具合同（给模型看的契约）

- **四个 Pydantic 参数模型**：
  - `CityPOS`（`city_name`，`model.py:5-7`）
  - `CityWeather`（`latitude`/`longitude`，`model.py:9-11`）
  - `CityQuality`（`latitude`/`longitude`，`model.py:14-16`）
  - `RoomInfo`（`room_name`，`model.py:19-21`）
  - 字段均有中文 `Field(description=...)`，生成 JSON Schema 时成为参数说明。
- **四个工具合同字典**：`city_tool`、`weather_tool`、`quality_tool`、`room_tool`（`model.py:25-63`），每个含 `type: "function"`、`name`（`get_city_pos` / `get_weather` / `get_quality` / `get_room_info`）、`description`、`strict: True`，参数来自 `model_json_schema()`。
- **`TOOLS`**（`model.py:66`）：四个合同的列表，是传给模型的工具声明。

> 合同与执行分离：合同名必须与 `tools.py` 里 `tools_map` 的键一致；模型侧只看到合同，执行侧只认注册表。

### `tools.py` — 工具实现与注册表

- **`get_city_pos(city_name)`**（`tools.py:12-28`）：aiohttp 调 open-meteo 地理编码接口，参数固定 `count=5&language=zh&countryCode=CN`（国家被硬编码为中国）。返回 `{"status": "success", "message": "查询成功", "data": res}`。`tools.py:19-23` 有一段被注释掉的非 200 状态检查。
- **`get_weather(latitude, longitude)`**（`tools.py:32-40`）：调 open-meteo forecast，`current` 取温度/相对湿度/风速，`hourly` 取温度。
- **`get_quality(latitude, longitude)`**（`tools.py:44-52`）：调 open-meteo air-quality，`current` 取 `european_aqi, pm10, pm2_5, nitrogen_dioxide, ozone`，`timezone=Asia/Shanghai`。
- **`load_meeting_rooms()`**（`tools.py:56-61`）：读 `data/meeting_rooms.json`，`JSONDecodeError`/`OSError` 或非列表时容错返回 `[]`。
- **`get_room_info(room_name)`**（`tools.py:65-95`）：先按 `name` 精确匹配（`tools.py:75-81`）；不中再按"名称包含输入"模糊匹配，命中多个则整个 `matched` 列表返回（`tools.py:83-89`）；都找不到返回 `status: "error"` 且 message 提示确认名称（`tools.py:91-95`）。
- **`tools_map`**（`tools.py:99-116`）：执行侧注册表，名字 → `{"function": 函数, "args": Pydantic 模型}`，四对映射。

> `tools.py:1` 导入了 `requests` 但全文件未使用（遗留导入）。

### `service.py` — 受控循环核心

- **模块级环境配置**（`service.py:14-24`）：`load_dotenv()` 读 `.env` 的 `OPENAI_API_KEY` / `OPENAI_MODEL` / `BASE_URL`，缺任一直接 `raise RuntimeError`。
- **`trim(messages, max_rounds)`**（`service.py:28-40`）：裁剪历史。`max_rounds` 为负抛 `ValueError`；`max_rounds == 0` 只保留 system；否则保留 `system.copy()` + 最后 `max_rounds * 2` 条（每轮 user+assistant 两条）。
- **`RunResult(ok, answer, trace)`**（`service.py`）：`run()` 的统一返回结构。`ok` 表示是否拿到最终回答；`answer` 为最终回答或 `None`；`trace` 为本轮结构化轨迹。
- **轨迹记录**：已抽离到 `trace.py` 的 `TraceRecorder`，`service.py` 只负责在模型请求、工具轮次、工具调用和最终回答处调用记录方法。
- **`UserService.__init__`**：建 `AsyncOpenAI` 客户端，并创建 `Tracks("data/tracks.json")`。
- **`send(messages)`**：异步调用 `chat.completions.create`，`tools=TOOLS`、`tool_choice="auto"`、`parallel_tool_calls=True`（允许同轮多个工具调用）。
- **`run(messages, user_messages, recorder=None)`**：一次完整工具闭环，返回 `RunResult`。
  1. 先 `trim(..., max_rounds=5)` 裁剪传入消息，记录 `start_index` 后追加 user 消息；默认创建 `trace.TraceRecorder`。
  2. `for i in range(MAX_MODEL_ROUNDS)` 最多 10 轮：每次模型请求记录次数、耗时和 `usage` Token；模型调用异常则返回失败 `RunResult`（`stop_reason="model_request_failed"`）。
  3. 有 `tool_calls` 时：先把 assistant 消息 `model_dump(exclude_none=True)` 并强制补 `content=""` 追加进消息——保证消息顺序：assistant 在前、tool 结果在后；再开启工具轮次记录。
  4. 用 `asyncio.gather(..., return_exceptions=True)` **并发**执行所有工具，每个调用由 `_execute_tool()` 记录开始/结束/耗时/结果/错误；异常经 `sanitize_error()` 分类脱敏，回传给模型仍是 `{"ok": False, "error": "tool_failed"}`。
  5. 无 `tool_calls` 时视为最终回答：追加 assistant 消息、把 `messages[start_index:]`（本轮完整轨迹）存入 `Tracks`，返回 `RunResult(True, answer, trace)`；工具调用有失败时整体状态为 `partial`。
  6. 空最终回答返回 `stop_reason="empty_answer"` 的失败结果；循环耗尽返回 `stop_reason="max_model_rounds"` 的失败结果，不再抛未处理异常。
- **`_execute_tool(tool, call_entry, recorder)`**（`service.py:200-227`）：单个工具的执行包装，负责起始时间、异常分类、失败结果与轨迹写入。
- **`run_tools(tool)`**（`service.py:229-257`）：单个工具的安全执行链。
  1. 打印 tool id/名称/参数。
  2. `tools_map.get(...)` 白名单查询，查不到抛 `RuntimeError("访问的工具不存在！")`（`service.py:235-237`）。
  3. `json.loads` 解析模型参数（禁 eval，失败抛异常，`service.py:240-243`）。
  4. Pydantic `model_validate` 校验（`service.py:246-249`）。
  5. `await curr_tool["function"](**args.model_dump())` 执行（`service.py:252-257`）。

> 与根目录 CLAUDE.md 描述略有出入的实际行为：解析失败、校验失败、执行失败在 `run_tools` 中都只是 `raise RuntimeError`，回传给模型的仍是统一的 `{"ok": False, "error": "tool_failed"}`；但 `trace.py` 会根据异常文本细分为 `tool_not_found` / `argument_parse_failed` / `validation_failed` / `timeout` / `tool_execution_failed`，页面展示的是细分后的类型和脱敏消息。工具自身返回的 `status: "error"`（如会议室未找到）在轨迹中标记为 `tool_reported_error`。

### `trace.py` — 本轮轨迹采集

- **`TraceRecorder(question)`**：一轮对话一个实例，初始化 trace_id、问题、状态、开始时间、模型/工具计数、Token 汇总、轮次列表与错误占位。
- **模型请求**：`begin_model_request()` / `finish_model_request(started_perf, usage, ok)` 记录请求次数、每次耗时（汇总为 `model_duration_ms`）、输入/输出/总 Token。
  - `usage` 支持 OpenAI 对象或字典；全部请求返回时 `complete=true`，部分/全部缺失时 `complete=false`，缺失值保持 `null`；
  - `total_tokens` 缺失时用实际返回的输入 + 输出相加，不按字符估算。
- **工具轮次**：`begin_tool_round(tool_calls)` / `finish_tool_round(round_entry)` 记录轮次编号、调用数量、`single`/`parallel`、轮次起止与真实墙钟耗时；未完成的调用会被标记失败，不能显示为成功。
- **工具调用**：`start_tool_call()` / `finish_tool_call()` 记录调用 id、名称、用途、参数、结果、状态、错误类型/消息、开始/结束时间与耗时。
- **整体收尾**：`finish(status, stop_reason, error)` 写入状态、停止原因、结束时间、总耗时，并推导 `execution_mode`（`none`/`serial`/`parallel`/`mixed`）。
- **错误处理**：
  - `classify_error()` 将异常细分为 `tool_not_found`、`argument_parse_failed`、`validation_failed`、`timeout`、`tool_execution_failed`；
  - `sanitize_error()` 只返回固定可读消息；
  - `redact_text()` 清理密钥、Bearer 认证头、Windows/Unix 本机路径与异常堆栈。
- **工具用途说明**：`TOOL_DESCRIPTIONS` 从 `model.py` 的 `TOOLS` 自动生成，避免与工具合同重复维护。
- **单元测试**：`tests/test_trace.py` 共 19 项，覆盖无工具、单工具、并行、多轮混合、Token 缺失/部分/累计、错误分类与脱敏、未完成调用、JSON 可序列化。

### `history.py` — 会话历史持久化

- **`History.__init__(history_path)`**（`history.py:5-9`）：转成 `Path`、`mkdir(parents=True, exist_ok=True)` 建父目录、`load()` 载入 `self.messages`。
- **`load()`**（`history.py:11-24`）：文件不存在返回 `[]`；解析失败容错返回 `[]`；**过滤掉 `role == "assistant"` 且 content 为空的字典**——防止历史上只含 `tool_calls` 而 content 为空的 assistant 消息被再次发给模型（因为对应的 tool 结果没存进历史）。
- **`save(messages)`**（`history.py:26-30`）：`json.dumps(..., ensure_ascii=False, indent=4)` 写入，保证中文可读。

### `tracks.py` — 调用轨迹持久化

- **`Tracks.__init__(path)`**（`tracks.py:7-10`）：建父目录。
- **`load()`**（`tracks.py:12-20`）：容错读 JSON 列表，失败或非列表返回 `[]`。
- **`save(track)`**（`tracks.py:23-29`）：`load()` 出旧列表 → `append(track)` → 整体写回。**追加式**存储：`data/tracks.json` 中每个元素是一条 `{"id": ..., "tracks": [本轮完整消息轨迹]}`，用于事后复盘模型每次调用了哪些工具、传了什么参数。

### `data/meeting_rooms.json`

6 间会议室（星辰/望岳/云帆/听雨/凌云/听涛），字段：`name`、`address`、`floor`、`capacity`（6–50 人）、`equipment` 列表。是 `get_room_info` 的数据源，也是 `/rooms` 命令展示的内容。

## 值得注意的细节

1. **`tools.py:1` 的 `import requests` 是死导入**，整个文件只用 aiohttp。
2. **`tools.py:19-23` 状态码检查被注释掉**，HTTP 非 200 时不会按注释所示返回 error，而会走 aiohttp 自身的异常路径。
3. **`service.py:99` 注释编号跳过了 "3."**（只有 1、2、4），纯注释瑕疵。
4. `get_city_pos` 把 `countryCode=CN` 写死，模型侧无论用户问哪个国家，地理编码都限定在中国。
5. `main.py` 的 `messages` 里 system 一直存在，但持久化（`history.save(messages[1:])`）和 `trim()` 都刻意把它排除在对话体之外，下次启动再由 `main()` 重新拼回。
